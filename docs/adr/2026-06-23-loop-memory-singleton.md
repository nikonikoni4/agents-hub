# Loop内存单例策略

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

Loop功能在实现过程中，发现了一个严重的内存管理问题：加载Loop时会全量加载所有定义的Loop到内存中，并且没有任何清除机制，导致内存无限扩大。同时，一个群聊中同时执行多个Loop会导致文件修改相互影响，增加复杂度和出错概率。

### 讨论范围

- Loop的内存管理策略
- Loop的加载和清除机制
- 一个群聊中同时执行多个Loop的可行性

### 非讨论范围

- Loop的具体执行逻辑
- Loop的持久化策略
- Loop的API设计

### 模糊信息的明确定义

- `激活`：指Loop存在于内存中，可以被查询和操作
- `单例`：内存中同时只能保持一个Loop实例

### 问题深度

这是一个涉及架构原则和长期维护方式的深层问题，直接影响Loop功能的内存管理、并发控制和错误处理。

## 现状

1. **内存问题**：加载Loop时会全量加载所有定义的Loop到内存中，没有清除机制，导致内存无限扩大
2. **并发问题**：一个群聊中如果同时执行多个Loop，Loop定义文件（loops.jsonl）会被多个执行实例修改，导致数据不一致
3. **复杂度问题**：多个Loop同时执行会增加状态管理的复杂度，容易出错
4. **现有约束**：LoopExecutionManager已经实现了"单execution保持策略"，内存中同时只保持一个活跃的execution

## 可选方案

### 方案 A：全量加载，多Loop并行

将所有Loop定义加载到内存中，允许一个群聊同时执行多个Loop。

**优势**

- 可以同时执行多个Loop，提高并行度
- 查询任意Loop的状态不需要从文件加载

**劣势**

- 内存无限扩大，没有清除机制
- 多个Loop同时修改loops.jsonl文件，导致数据不一致
- 状态管理复杂度高，容易出错
- 与现有的"单execution保持策略"冲突

### 方案 B：单例策略，按需加载

内存中同时只能保持一个Loop，只有通过start_loop启动的Loop才会加载到内存。

**优势**

- 内存占用固定，不会无限扩大
- 避免文件修改冲突，保证数据一致性
- 状态管理简单，降低出错概率
- 与现有的"单execution保持策略"一致
- 支持懒加载，按需从文件读取Loop定义

**劣势**

- 不能同时执行多个Loop
- 查询非激活Loop需要从文件读取

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 全量加载 | 无 | 内存无限扩大，文件修改冲突 |
| v2 | 单例策略 | 内存问题，文件冲突 | 不能同时执行多个Loop |

## 最终决策

选择 `方案 B：单例策略，按需加载`。

## 决策原因

1. **内存安全**：单例策略保证内存占用固定，不会无限扩大，解决之前的内存bug
2. **数据一致性**：一个群聊同时只有一个Loop在内存中，避免loops.jsonl文件被多个执行实例修改
3. **复杂度控制**：单例策略简化了状态管理，降低出错概率
4. **架构一致性**：与现有的"单execution保持策略"保持一致，形成统一的内存管理模型
5. **实际需求**：大多数场景下一个群聊只需要执行一个Loop，多Loop并行的需求可以通过顺序执行满足

## 后续影响

1. **API设计**：前端需要通过list_loops获取Loop列表，通过get_loop_status或get_loop获取特定Loop的状态
2. **内存管理**：需要实现懒加载机制，按需从文件读取Loop定义
3. **状态查询**：非激活Loop的状态查询需要从文件读取，可能影响查询性能
4. **文档更新**：需要更新CONTEXT.md和相关spec，明确单例策略的约束
