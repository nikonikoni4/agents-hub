# Loop MVP 限制说明

**文档版本**: 1.0  
**创建日期**: 2026-06-19  
**适用范围**: Loop 循环功能 MVP 阶段

---

## 概述

本文档列出 Loop（循环）功能在 MVP 阶段的所有已知限制和约束。这些限制是为了简化初期实现、降低复杂度、快速验证核心价值而设定的。未来版本可能会逐步放宽这些限制。

---

## 循环结构限制

### 1. 节点数量限制

**限制内容**：
- 一个 Loop 至少需要 2 个节点
- 没有节点数量上限，但建议不超过 5 个（性能和可维护性考虑）

**理由**：
- 循环至少需要 2 个参与者才有意义（如 Executor + Reviewer）
- 过多节点会增加循环复杂度和调试难度

**影响**：
- 无法创建单节点循环（如"自我审查"）
- 复杂的多节点流程可能需要拆分成多个循环

---

### 2. 单一 TERMINATOR 节点

**限制内容**：
- 一个 Loop 有且仅有 1 个 TERMINATOR 节点
- TERMINATOR 节点必须明确存在，不能全部是 NORMAL 节点

**理由**：
- 简化退出逻辑，避免多个判断点的冲突
- 明确哪个节点负责决定循环是否结束

**影响**：
- 无法在多个节点设置判断点（如"Executor 也可以判断放弃"）
- 所有退出判断必须由唯一的 TERMINATOR 节点完成

**未来扩展**：Phase 2 可能支持多个 TERMINATOR 节点（任意一个返回 false 即退出）

---

### 3. 节点顺序固定

**限制内容**：
- 节点按照创建时的顺序循环执行（Node0 → Node1 → ... → NodeN → Node0）
- 无法跳过节点、动态调整顺序或实现分支逻辑

**理由**：
- 固定顺序简化调度逻辑，易于理解和调试
- 分支逻辑需要复杂的决策机制（Manager 判断），不适合 MVP

**影响**：
- 无法实现"根据结果选择下一个节点"的复杂流程
- 所有节点必须每轮都执行（即使某些节点可能不需要）

**未来扩展**：Phase 2 可能支持 LoopType.MANAGED，Manager 动态决定下一步

---

### 4. 循环定义不可变

**限制内容**：
- Loop 创建后，节点列表、输出格式要求、最大循环次数等配置不可修改
- 如需调整，必须删除旧循环并创建新循环

**理由**：
- 运行中修改配置会引入状态不一致问题
- 简化实现，避免复杂的配置版本管理

**影响**：
- 发现配置错误时，必须停止循环、删除、重新创建
- 无法在运行中动态调整策略（如增加重试次数）

**未来扩展**：Phase 2 可能支持 PAUSED 状态下的配置修改

---

## 执行与调度限制

### 5. 串行执行，无并行节点

**限制内容**：
- 节点必须串行执行，一次只有一个节点在工作
- 无法同时执行多个节点（如"Reviewer A 和 Reviewer B 并行审查"）

**理由**：
- 并行执行需要复杂的同步和合并逻辑
- MVP 专注验证串行循环的核心价值

**影响**：
- 多个审查者场景无法并行，必须串行审查
- 循环执行时间较长（所有节点顺序执行）

**未来扩展**：Phase 2 可能支持并行节点组

---

### 6. 单群聊单循环限制

**限制内容**：
- 一个 GroupChat 同时只能有一个 RUNNING 状态的 Loop
- 创建新循环前，必须先删除或完成旧循环

**理由**：
- 避免资源竞争（Agent 状态、消息队列）
- 简化管理，降低出错概率

**影响**：
- 无法同时运行多个循环（如"代码审查循环"和"文档优化循环"）
- 必须串行处理多个循环任务

**未来扩展**：未来可能放宽为"单 Agent 单循环"（Agent 不能同时参与多个循环）

---

### 7. 无嵌套循环支持

**限制内容**：
- 循环内的节点不能再创建子循环
- 不支持"循环中的循环"

**理由**：
- 嵌套循环大幅增加状态管理复杂度
- MVP 专注单层循环验证

**影响**：
- 复杂的嵌套场景（如"每次执行都需要内部子审查"）无法实现
- 必须手动展开为单层循环

**未来扩展**：Phase 3 可能支持嵌套循环

---

### 8. 无暂停后恢复功能

**限制内容**：
- `stop_loop()` 将循环状态设为 PAUSED，但没有 `resume_loop()` 工具
- PAUSED 状态的循环只能删除，无法恢复执行

**理由**：
- 恢复需要保存和恢复循环中间状态（当前节点、输出缓存等）
- MVP 专注"一次性执行"场景

**影响**：
- 停止后无法继续，必须重新启动新循环
- 适合"发现问题就重来"的场景，不适合长时间中断的场景

**未来扩展**：Phase 2 可能支持 `resume_loop()`

---

## 上下文与消息限制

### 9. 完全隔离群聊历史

**限制内容**：
- 循环节点只能看到循环专用上下文（节点职责、输出格式、上一节点输出）
- 无法访问群聊历史消息、压缩历史、其他成员对话

**理由**：
- 循环任务通常是专注的、重复的，群聊历史是噪音
- 隔离后 Agent 更专注当前任务

**影响**：
- 节点无法引用群聊中的背景信息（如"参考之前讨论的架构设计"）
- 需要在 `initial_task` 中包含所有必要的背景信息

**缓解方案**：Manager 创建 Loop 时，将必要背景写入 `initial_task`

**未来扩展**：Phase 2 可能支持"可选引用群聊历史"配置

---

### 10. 只看上一节点输出，无记忆

**限制内容**：
- 每个节点只能看到"上一个节点的输出"
- 无法看到本轮循环的所有历史（如"第一次审查意见"）
- 无法看到上一轮循环的内容

**理由**：
- 简化上下文构造逻辑
- 减少 token 消耗

**影响**：
- Reviewer 无法看到 Executor 的多次修改记录
- Executor 无法参考"上一轮我是怎么做的"

**设计trade-off**：讨论中曾考虑"看本轮所有消息"，但为简化实现暂时只看上一节点

**未来扩展**：Phase 2 可能支持"循环内历史"配置

---

## 输出与校验限制

### 11. 简单字符串匹配校验

**限制内容**：
- 输出校验只使用简单的字符串包含检查（`field in output`）
- 不校验字段的值是否正确、格式是否规范

**理由**：
- 简单匹配实现快、性能好、易于理解
- 避免引入复杂的 Markdown 解析器

**影响**：
- 无法检测"字段存在但值为空"
- 无法检测"字段出现在代码块中（不是实际输出）"
- 可能产生误判（字段出现在其他地方）

**缓解方案**：通过清晰的输出格式提示词引导 Agent 正确输出

**未来扩展**：Phase 2 可能支持更严格的结构化解析

---

### 12. 固定重试次数

**限制内容**：
- 输出校验失败的重试次数固定为 3 次（`max_retries=3`）
- 无法为不同节点设置不同的重试次数

**理由**：
- 3 次重试是经验值，适合大多数场景
- 简化配置，降低复杂度

**影响**：
- 复杂任务可能需要更多重试（但 MVP 固定 3 次）
- 简单任务可能浪费重试机会

**未来扩展**：可能支持节点级的 `max_retries` 配置（已在数据模型中预留）

---

### 13. TERMINATOR 节点必须同时校验业务字段和退出标签

**限制内容**：
- TERMINATOR 节点的输出必须同时包含：
  1. 业务字段（如 `# 审查意见`、`**审查结果**`）
  2. 退出决策标签（`<loop_decision>`）
- 缺少任何一个都会校验失败

**理由**：
- 确保 TERMINATOR 节点既给出业务反馈，又控制循环流程
- 避免"只判断不反馈"或"只反馈不判断"的问题

**影响**：
- TERMINATOR 节点的输出格式要求更严格
- 必须同时满足两套校验规则

**未来扩展**：暂无放宽计划，这是设计约束

---

## 控制与管理限制

### 14. 只有 Manager 可操作循环

**限制内容**：
- 只有 LEADER 角色（Manager）可以调用循环相关的 MCP 工具
- Worker 和 User 无法创建、启动、停止、删除循环

**理由**：
- Manager 负责任务编排，循环是编排的一种形式
- 避免权限混乱，简化安全模型

**影响**：
- User 无法直接控制循环（必须通过 Manager）
- Worker 无法"自行退出循环"或"请求暂停"

**未来扩展**：Phase 2 可能支持更细粒度的权限控制

---

### 15. 创建后需要手动启动

**限制内容**：
- `create_loop()` 只创建循环（状态 CREATED），不自动启动
- 必须调用 `start_loop()` 才能开始执行

**理由**：
- 预留审核扩展点（未来 User 可以在启动前审核 Loop 定义）
- 分离创建和启动，责任更清晰

**影响**：
- Manager 需要两步操作（create → start）
- 增加操作步骤，但换来灵活性

**未来扩展**：可能提供 `create_and_start_loop()` 快捷工具

---

### 16. 无前端专用 UI

**限制内容**：
- MVP 没有前端的循环创建/管理 UI
- 所有操作通过 Manager 在群聊中自然语言完成（如"创建一个执行-审查循环"）

**理由**：
- MVP 专注后端核心逻辑验证
- 前端 UI 开发成本高，暂时延后

**影响**：
- 用户体验依赖 Manager 的理解能力
- 无法可视化查看循环状态、历史、进度

**未来扩展**：Phase 2 专门的前端循环管理模块

---

## 错误处理限制

### 17. 无分级错误恢复

**限制内容**：
- 任何异常（节点执行失败、校验超时、系统异常）都会导致循环立即 FAILED
- 无法区分"可恢复错误"和"不可恢复错误"

**理由**：
- 分级恢复需要复杂的错误分类和恢复策略
- MVP 采用"fail-fast"原则

**影响**：
- 临时网络波动也会导致循环失败（无自动重试）
- 必须手动重新启动循环

**未来扩展**：Phase 2 可能支持"可恢复错误自动重试"

---

### 18. 无循环回滚功能

**限制内容**：
- 循环失败后，已执行的操作不会自动回滚
- 节点产生的副作用（如文件修改）会保留

**理由**：
- 回滚需要节点支持"撤销操作"，复杂度高
- 大多数场景下，保留部分结果反而有价值

**影响**：
- 失败后需要手动清理或继续处理
- 适合"幂等操作"或"失败继续"的场景

**未来扩展**：Phase 3 可能支持事务性循环（可回滚）

---

## 性能与规模限制

### 19. 同步等待节点完成

**限制内容**：
- LoopExecutor 发送消息后，同步等待节点完成（阻塞在 `completion_queue.get()`）
- 无法异步触发多个节点

**理由**：
- 串行执行要求前一个节点完成后才能执行下一个
- 简化调度逻辑

**影响**：
- 循环执行时间 = 所有节点执行时间之和
- 适合"快速迭代"场景，不适合"长时间任务"

**未来扩展**：并行节点支持后可能改进

---

### 20. 节点执行超时固定为 5 分钟

**限制内容**：
- LoopExecutor 等待节点完成的超时时间固定为 5 分钟（300 秒）
- 超时后检查 Agent 状态：如果为 "error" 则判定为 CLI 执行失败，否则判定为超时
- 无法为不同节点设置不同的超时时间

**理由**：
- 5 分钟是经验值，适合大多数场景
- 固定超时简化配置
- 利用 Agent.status 判断超时原因，避免修改 Agent.run() 异常处理逻辑

**影响**：
- 复杂任务可能需要更长超时（但 MVP 固定 5 分钟）
- 超时发生时，循环立即失败（status=FAILED）

**未来扩展**：Phase 2 可能支持节点级超时配置

---

### 21. IN_LOOP 状态下禁止手动操作 Agent

**限制内容**：
- Agent 在循环中时（status="in_loop"），前端应禁用以下操作按钮：
  - 重置 (reset)：会清空会话，破坏循环状态
  - 压缩 (compact)：会修改上下文，与循环隔离冲突
  - 暂停 (pause)：会停止 CLI，与 stop_loop 冲突
  - 发送消息：Agent 在 loop 中不接受外部消息
- 只读操作（查看历史）允许

**理由**：
- 避免外部操作干扰循环执行
- 循环状态由 LoopExecutor 独占管理

**影响**：
- 用户无法在循环执行期间手动干预参与的 Agent
- 必须先 stop_loop() 才能操作 Agent

**实现方式**：前端根据 `AgentMemberInfo.status === "in_loop"` 禁用按钮（后端不强制）

**未来扩展**：Phase 2 可能支持"循环暂停期间允许手动操作"

---

### 22. 状态切换时不处理队列残留消息

**限制内容**：
- Agent 从 IDLE 切换到 IN_LOOP 状态时，message_queue 中已有的待处理消息会被 `_should_accept_message()` 拒绝并丢弃
- 不会清空队列，也不会通知发送方

**理由**：
- MVP 假设 Agent 在 idle 状态下队列为空
- 清空队列或通知发送方会增加复杂度

**影响**：
- 如果 Agent 有未完成的任务，启动 Loop 会导致消息丢失
- 正常流程下不应该发生（idle 状态下队列应该空）

**未来扩展**：Phase 2 可能在 start_loop 前检查队列是否为空，非空时拒绝启动

---

### 23. loop_context 无大小限制

**限制内容**：
- loop_context 包含完整的节点职责描述和上一节点输出
- 如果上一节点输出很长（如完整代码实现），metadata 可能非常大
- 当前没有大小限制或截断机制

**理由**：
- MVP 阶段先验证功能可行性
- 大部分场景下输出不会过长

**影响**：
- 上一节点输出过长时，可能导致内存或序列化问题
- AgentMessage.metadata 体积可能过大

**未来扩展**：Phase 2 可能实现输出截断机制（保留前 N 字符）或引用机制（只传递输出 ID）

---

## 数据与持久化限制

### 24. 只持久化 Loop 状态，不持久化中间输出

**限制内容**：
- `loops.jsonl` 只保存 Loop 的状态变更记录（创建、启动、轮次增加、结束）
- 节点的中间输出只保存在群聊历史（`<group_chat_id>.jsonl`）

**理由**：
- 避免数据重复（群聊历史已有完整记录）
- 简化 Loop 持久化逻辑

**影响**：
- 查询循环历史需要同时读取 `loops.jsonl` 和群聊历史
- 无法"只看循环消息"（需要过滤群聊历史）

**未来扩展**：Phase 2 可能提供"循环消息过滤视图"

---

### 25. 循环历史无自动清理

**限制内容**：
- 已完成/失败的循环记录永久保留
- 没有自动归档或清理机制

**理由**：
- MVP 专注核心功能，清理策略延后
- 保留历史有助于调试和复盘

**影响**：
- 长时间运行可能积累大量循环记录
- 需要手动删除不需要的循环

**未来扩展**：Phase 2 可能支持自动归档（保留 N 天）

---

## 可扩展性限制

### 26. 无 Hook 机制

**限制内容**：
- 不支持 Before/After Agent Call Hook
- 无法在节点执行前后插入自定义逻辑

**理由**：
- 避免与未来的全局 Hook 机制冲突
- 简化初期实现

**影响**：
- 无法在循环中插入额外的校验、日志、通知逻辑
- 所有逻辑必须由节点自己完成

**未来扩展**：全局 Hook 机制成熟后，Loop 可能复用

---

### 27. 无动态节点注入

**限制内容**：
- 循环运行中无法添加或删除节点
- 节点列表在创建时固定

**理由**：
- 动态修改节点会引入状态不一致问题
- MVP 专注静态流程验证

**影响**：
- 无法实现"根据结果动态增加审查者"
- 必须重新创建循环

**未来扩展**：Phase 3 可能支持动态编排

---

## 总结

### MVP 设计哲学

Loop MVP 遵循以下原则：
1. **简单优于灵活**：固定顺序、单一 TERMINATOR、串行执行
2. **隔离优于集成**：完全隔离群聊历史、单群聊单循环
3. **快速失败优于智能恢复**：fail-fast、无自动重试、无回滚
4. **可扩展优于完美**：预留扩展点（LoopType、decision_points、并行节点）

### 何时放宽限制？

根据用户反馈和实际使用情况，未来版本可能依次放宽：
- **Phase 2**（优先级高）：Manager 判断模式、节点级超时、暂停恢复、前端 UI
- **Phase 3**（优先级中）：嵌套循环、并行节点、动态编排、Hook 集成
- **Phase 4**（优先级低）：事务性循环、多群聊并行、高级错误恢复
