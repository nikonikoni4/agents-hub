### 二、设计优化（4 项）

#### 6. ✅ 重试机制修正 - AgentCall 只创建一次

**问题**：原设计每次重试都创建新 AgentCall，语义错误

**修正方案**：
- AgentCall 只创建一次（一个任务 = 一个 call）
- 重试消息复用同一个 call_id
- 重试消息格式：`[循环-节点{agent}-第{iteration}轮-重试{retry_count}]`
- 超过重试次数后，AgentCall 状态更新为 FAILED

**修改文件**：
- `slice-4-output-validation-retry.md`：自动重试机制章节

---

#### 7. ✅ stop_loop 竞态条件 - 新增终止信号机制

**问题**：stop_loop 停止 CLI 后，LoopExecutor 会永久阻塞在 completion_queue.get()

**修正方案**：
- stop_loop 流程第一步：向 completion_queue 发送终止信号
  - 信号格式：`{"loop_id": loop_id, "is_termination_signal": True}`
- LoopExecutor 接收到终止信号后退出循环

**修改文件**：
- `slice-7-mcp-tools.md`：stop_loop 流程增加步骤 0

---

#### 8. ✅ TERMINATOR 解析健壮性 - 增强正则表达式

**问题**：XML 解析可能因大小写、空格变化而失败

**修正方案**：
- 使用正则表达式：`r'<loop_decision[^>]*>(.*?)</loop_decision>'`
- 忽略大小写和空格：`re.DOTALL | re.IGNORECASE`

**修改文件**：
- `slice-4-output-validation-retry.md`：TERMINATOR 节点特殊校验章节

#### 9. ✅ 并发控制 - LoopManager 加锁

## 关键设计决策回顾

### 1. 为什么选择 MessageType.LOOP_MESSAGE？

**方案对比**：
- 方案 A：循环消息不自动保存，由 LoopExecutor 控制 → 但需要 LoopExecutor 拿到完整 AgentResult
- **方案 B（采用）**：引入新消息类型，保存控制权在 LoopExecutor → 职责清晰，扩展性好
- 方案 C：所有消息都保存，标记重试消息 → 需要消息更新机制，复杂度高

**扩展性验证**：
- 未来节点需要外部干预：通过 LoopNode 字段判断，消息类型不变 ✅
- 条件分支：通过 LoopNode 字段判断，消息类型不变 ✅
- 通知 Manager：用 NOTIFICATION，消息类型不变 ✅

**影响范围**：3 处局部修改（MessageType 枚举、Agent.run()、LoopExecutor）

---

### 2. 为什么完成通知传递 AgentResult？

**问题**：
- LoopExecutor 需要保存消息到群聊历史
- 但只有 output 字符串，缺少 timestamp、platform 等字段

**方案对比**：
- 方案 A：完成通知只传 output，LoopExecutor 手动构造消息 → 字段来源不清晰
- **方案 B（采用）**：完成通知传递完整 AgentResult → 简单直接，包含完整信息

**优点**：
- 解决"LoopExecutor 如何获取完整结果"的问题
- 内存传递，性能无问题
- 包含 modified_files、git_diff 等扩展字段

---

### 3. 为什么超时后检查 Agent 状态？

**问题**：
- Agent CLI 报错时，LoopExecutor 永久阻塞
- 原设计：Agent 发送失败通知（success=False）→ 需要修改 Agent.run() 异常处理

**方案对比**：
- 方案 A：Agent.run() 捕获异常后发送失败通知 → 需要修改 Agent.run() 结构
- **方案 B（采用）**：LoopExecutor 超时后检查 Agent.status → 利用现有机制，无需修改 Agent

**优点**：
- 不需要修改 Agent.run() 的异常处理逻辑
- 利用现有的 Agent.status 机制
- 超时机制防止永久阻塞
