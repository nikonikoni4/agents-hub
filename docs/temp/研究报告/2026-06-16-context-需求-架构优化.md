### 1.5 并发场景理解

**阅读**：`group_chat.py` 的 `_start_agent_tasks()` 方法

**发现**：
```python
def _start_agent_tasks(self):
    self.manager_task = asyncio.create_task(self.manager.run())
    for name, w in self.workers.items():
        task = asyncio.create_task(w.run())  # ← 并行启动多个 worker
        self.worker_tasks[name] = task
```

**理解**：
- 一个群聊可以有多个 Agent（1 Manager + N Workers）
- 所有 Agent 的 `run()` 任务**并行执行**（asyncio.create_task）
- 如果每个 Agent 都动态写 CLAUDE.md，会产生文件竞态

**旧方案问题**：
- Agent A 写入 `<AGENT_RUNTIME>BlockA</AGENT_RUNTIME>`
- Agent B 同时写入 `<AGENT_RUNTIME>BlockB</AGENT_RUNTIME>`
- 最后一个写入者覆盖前者，导致 Agent A 看到 B 的 runtime

### 1.6 新旧方案对比

| 维度 | 旧方案（文件注入） | 新方案（参数注入） |
|------|-------------------|-------------------|
| **注入目标** | 写入 CLAUDE.md/AGENTS.md | CLI `--append-system-prompt` |
| **竞态风险** | ✅ 存在（多 Agent 写同一文件） | ❌ 无（每次调用独立传参） |
| **实现复杂度** | 需要标记替换逻辑 | 简单传参 |
| **调试友好性** | 低（需查看文件） | 高（参数可记录） |
| **当前状态** | 已废弃（代码注释） | 已实现但未启用 |

**疑问**：为什么参数传递已实现，但 `system_prompt = None`？

### 3.5 常见困惑 FAQ

**Q1: system_prompt 参数为什么保留但不用？**
A: 历史原因 + 未来扩展：
- Commit e2624d7 实现了参数通道（为了解决竞态）
- Commit 0a43f44 把 runtime 移到 user message（不再需要动态 system prompt）
- 保留参数是为了：
  1. 未来可能需要传递其他动态内容
  2. 代码兼容性（删除参数需要改所有调用点）
  3. OpenCode 平台仍使用文件注入（见 `_build_opencode_system_prompt`）

**Q2: CLAUDE.md/AGENTS.md 现在写什么？**
A: 静态内容（Role 创建时写入）：
- 平台信息（Claude/Codex 使用说明）
- Agent 身份（角色名、描述）
- 工具使用说明（MCP 工具列表）
- 规则和约束（共享规则）

参考：`roles/prompt_file.py` 的 `write_prompt_file()`

**Q3: Runtime 为什么要在 user message？**
A: 架构决策（从 commit 0a43f44 推断）：
- System prompt = 静态上下文（整个会话不变）
- User message = 动态上下文（每次调用不同）
- Runtime 信息（team_members、call_id）每次调用都可能变化
- 移到 user message 后：
  - 无需动态生成 system prompt
  - 无需写文件
  - 无竞态风险
