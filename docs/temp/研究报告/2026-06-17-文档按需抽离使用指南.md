# 文档按需抽离 - 使用指南

## 快速开始

### 1. 安装依赖

```bash
pip install pyyaml
```

### 2. 使用脚本

```bash
# 基本用法
python doc_extract.py <文档路径> --task-type <类型> --depth <深度> --focus <关注点>

# 输出到文件
python doc_extract.py <文档路径> --task-type <类型> --depth <深度> --focus <关注点> -o output.md
```

### 3. 参数说明

| 参数 | 可选值 | 说明 |
|------|--------|------|
| `--task-type` | feature, bugfix, architecture, docs, style | 任务类型 |
| `--depth` | shallow, medium, deep | 深度级别 |
| `--focus` | frontend, backend, api, concurrency, architecture, docs | 关注点（可多选） |

## 使用场景

### 场景 1：实现新功能（前端）

**任务**：在聊天界面添加文件上传按钮

**命令**：
```bash
python doc_extract.py docs/specs/file-upload.md \
  --task-type feature \
  --depth shallow \
  --focus frontend \
  -o context.md
```

**抽离内容**：
- 数据契约（UploadedFileInfo 结构）
- API 端点（上传接口）
- 已知限制（文件大小、支持类型）

### 场景 2：实现新功能（后端）

**任务**：实现文件上传的存储和验证逻辑

**命令**：
```bash
python doc_extract.py docs/specs/file-upload.md \
  --task-type feature \
  --depth medium \
  --focus backend \
  -o context.md
```

**抽离内容**：
- 数据契约
- API 端点
- 业务规则（文件类型处理、验证逻辑）
- 数据转换（存储路径、格式转换）
- 已知限制

### 场景 3：修复 Bug

**任务**：修复文件上传后 Agent 无法读取的问题

**命令**：
```bash
python doc_extract.py docs/specs/file-upload.md \
  --task-type bugfix \
  --depth medium \
  --focus backend api \
  -o context.md
```

**抽离内容**：
- 数据流图（定位问题点）

```bash
  -o context.md
```

**抽离内容**：

- 演进历史（了解历史决策）

## 编写文档规范

### 1. 添加 YAML frontmatter

在文档开头添加元数据：

```markdown
---
doc_type: spec  # 或 flow
module: file_upload
version: 1.0
---
```

### 2. 标记章节属性

在二级标题后添加 HTML 注释：

```markdown
## 数据契约 <!-- scenarios: [impl, debug], depth: essential -->

### UploadedFileInfo
...
```

### 3. 标记属性说明

#### scenarios（适用场景）

| 场景 | 说明 | 何时使用 |
|------|------|---------|
| `impl` | 实现新功能 | 需要写代码实现功能时 |
| `debug` | 问题排查 | 修复 Bug、排查错误时 |
| `review` | 代码审查 | 审查代码、理解设计时 |
| `arch` | 架构演进 | 重构、优化架构时 |

**默认值**：`[impl, debug, review, arch]`（所有场景）

**何时明确标记**：
- 只用于特定场景（如"演进历史"只用于 arch）
- 大部分场景不需要（如"测试用例"只用于 impl）

#### depth（深度级别）

| 深度 | 说明 | 何时使用 |
|------|------|---------|
| `essential` | 必读 | 不读就无法完成任务的核心信息 |
| `recommended` | 推荐 | 提升效率/质量的重要信息 |
| `deep` | 深入 | 理解设计意图、避免破坏性修改 |

**默认值**：`essential`

**判断标准**：
- essential：数据契约、API 端点、已知限制
- recommended：业务规则、数据流图、数据转换
- deep：设计意图、演进历史、调用链

#### requires（依赖章节）

某些章节必须先读其他章节才能理解，使用 `requires` 标记：

```markdown
## 调用链 <!-- scenarios: [debug, arch], depth: deep, requires: ["数据转换"] -->
```

脚本会自动补全依赖章节（按拓扑排序）。

### 4. 章节 ID 规则

章节 ID 由标题自动生成（slug 化）：

| 标题 | 章节 ID |
|------|---------|
| `## 数据契约` | `数据契约` |
| `## API 端点` | `api-端点` |
| `## 核心流程` | `核心流程` |

在 `requires` 中引用时，使用章节 ID。

### 5. 推荐的文档结构

#### Spec 文档

```markdown
---
doc_type: spec
module: <模块名>
---

# <功能名> 功能规格

## 概述 <!-- scenarios: all, depth: essential -->
（核心流程、业务目标）

## 数据契约 <!-- scenarios: [impl, debug], depth: essential -->
（数据结构、字段定义、类型约束）

## API 端点 <!-- scenarios: [impl, debug], depth: essential -->
（接口签名、请求/响应格式）

## 业务规则 <!-- scenarios: [impl, review], depth: recommended -->
（验证逻辑、状态转换、权限控制）

## 已知限制 <!-- scenarios: all, depth: essential -->
（不支持的场景、边界条件、临时方案）

## 测试用例 <!-- scenarios: [impl], depth: recommended -->
（正常流程、边界条件）
```

#### Flow 文档

```markdown
---
doc_type: flow
module: <模块名>
---

# <功能名> 设计文档

## 数据流图 <!-- scenarios: [debug, arch], depth: recommended -->
（Mermaid 图 + 代码位置索引）

## 数据转换 <!-- scenarios: [impl, arch], depth: recommended -->
（数据如何从一个形态变成另一个形态）

## 调用链 <!-- scenarios: [debug, arch], depth: deep, requires: ["数据转换"] -->
（完整的函数调用路径）

## 设计意图 <!-- scenarios: [review, arch], depth: deep -->
（为什么这样设计、权衡取舍）

## 演进历史 <!-- scenarios: [arch], depth: recommended -->
（重构时间线、遗留代码解释）
```

## 常见问题

### Q1: 是否需要标记所有章节？

**不需要**。使用默认值原则：
- 大部分章节是 `scenarios: all, depth: essential`
- 只标记例外情况（深入内容、特定场景、有依赖）

### Q2: 如何判断章节的深度？

**经验法则**：
- **essential**：回答"是什么"、"怎么用"
- **recommended**：回答"如何工作"、"数据流"
- **deep**：回答"为什么"、"如何演进"

### Q3: 章节太大怎么办？

如果一个章节包含多个层次，可以拆分为子章节：

```markdown
## 业务规则 <!-- scenarios: [impl], depth: essential -->

### 文件类型处理 <!-- depth: essential -->
...

### 并发控制 <!-- depth: deep -->
...
```

子章节继承父章节的 `scenarios`，但可以覆盖 `depth`。

### Q4: 依赖关系复杂怎么办？

一个章节可以依赖多个章节：

```markdown
## 复杂章节 <!-- requires: ["章节A", "章节B"] -->
```

脚本会递归补全所有依赖，按拓扑排序输出。

### Q5: 如何验证标记是否正确？

**方法 1**：用脚本抽离，检查结果
```bash
python doc_extract.py <文档> --task-type feature --depth shallow --focus frontend
```

看抽离的内容是否足够完成该任务。

**方法 2**：让 AI 用抽离后的文档完成任务，记录反馈
- 缺少必要信息 → 调整章节的 `scenarios` 或 `depth`
- 包含无关信息 → 调整章节标记，排除不需要的场景

## 最佳实践

### 1. 渐进式标记

不需要一次性标记所有文档：
1. 先标记高频模块（如 agent_call、group_chat）
2. 在真实任务中使用，收集反馈
3. 根据反馈调整标记规则
4. 逐步推广到其他模块

### 2. 标记时思考"消费者视角"

不要问"这个章节属于什么深度"，而要问：
- **谁在什么任务中会读这个章节？**
- **不读这个章节能完成任务吗？**

### 3. 保持文档原子性

每个章节应该是独立的、完整的：
- ✅ "数据契约"章节包含所有数据结构定义
- ❌ "数据契约（续）"章节是前面的补充

原子性章节便于抽离和重组。

### 4. 定期审查标记

随着项目演进，任务类型和关注点会变化，需要定期审查：
- 某些章节的 `scenarios` 是否还准确？
- 是否有新的场景需要定义？
- `depth` 划分是否合理？

## 故障排查

### 问题 1：抽离结果为空

**原因**：章节的 `scenarios` 不匹配任务类型

**解决**：
1. 检查文档的章节标记
2. 检查任务类型映射规则（`SCENARIO_MAPPING`）
3. 添加调试输出：
```bash
python -c "from doc_extract import DocExtractor; e = DocExtractor('doc.md'); e.parse(); print([s.metadata for s in e.sections])"
```

### 问题 2：依赖章节未包含

**原因**：章节 ID 不匹配

**解决**：
1. 检查 `requires` 中的章节 ID 是否与目标章节的 ID 一致
2. 章节 ID 是标题的 slug 化结果（小写、空格转连字符）
3. 使用调试输出查看所有章节 ID：
```bash
python -c "from doc_extract import DocExtractor; e = DocExtractor('doc.md'); e.parse(); print([s.id for s in e.sections])"
```

### 问题 3：输出编码错误（Windows）

**原因**：Windows 控制台默认 GBK 编码

**解决**：脚本已自动处理，或手动输出到文件：
```bash
python doc_extract.py doc.md ... -o output.md
```
