# 文档按需抽离方案 - 最终报告

**日期**：2026-06-17  
**核心思路**：文档写全，通过脚本按场景/深度参数抽离章节，提供定制化的文档视图

---

## 执行摘要

本方案解决的核心问题：**不同任务类型需要不同的文档上下文，但不想为每个场景维护独立文档**。

**解决方案**：
1. 文档完整编写（包含所有章节）
2. 每个章节标记属性（适用场景、深度级别、依赖关系）
3. 脚本根据任务参数（task_type, depth, focus）抽离相关章节
4. 自动补全依赖章节（通过拓扑排序）

**验证结果**：
- 浅层任务：209 行（只看 essential 章节）
- 中等任务：233 行（包含 essential + recommended 章节）
- 深度任务：256 行（包含所有章节 + 依赖解析）

**核心价值**：
- 文档写一次，多场景复用
- AI 获得精准上下文，避免信息过载
- 维护成本低（标记与内容在一起）

## 一、技术方案

### 1.1 章节标记语法

**采用方案**：YAML frontmatter + HTML 注释

**示例**：
```markdown
---
doc_type: spec
module: file_upload
version: 1.0
---

# 文件上传功能规格

## 概述 <!-- scenarios: [impl, debug, review, arch], depth: essential -->
...

## 数据契约 <!-- scenarios: [impl, debug], depth: essential -->
...

## 调用链 <!-- scenarios: [debug, arch], depth: deep, requires: ["数据转换"] -->
...
```

**标记属性**：
- `scenarios`：适用场景列表
  - `impl`：新功能实现
  - `debug`：问题排查
  - `review`：代码审查
  - `arch`：架构演进
- `depth`：深度级别
  - `essential`：必读（浅层任务也需要）
  - `recommended`：推荐（中等深度任务需要）
  - `deep`：深入（深度任务需要）
- `requires`：依赖的章节 ID（可选）

**优势**：
- HTML 注释在渲染时不可见，不影响文档可读性
- 标记与内容在一起，修改时不会遗漏
- YAML 解析成熟，扩展性强

### 1.2 场景参数设计

基于真实任务分析（docs/progress/tasks.md + 30 条 git commit），提炼出 3 个核心参数：

| 参数 | 类型 | 取值 | 说明 |
|------|------|------|------|
| `task_type` | enum | feature, bugfix, architecture, docs, style | 任务类型 |
| `depth` | enum | shallow, medium, deep | 深度级别 |
| `focus` | list | frontend, backend, api, concurrency, architecture, docs | 关注点 |

**真实任务统计**：
- 任务类型分布：新功能 35%、Bug修复 25%、架构优化 20%、文档 12%、样式 8%
- 深度分布：浅层 15%、中层 55%、深层 30%
- 关注点频率：前后端联动 40%、后端架构 25%、并发/状态 15%、前端 UI 12%、工具 8%

**参数映射**：
- `task_type` → `scenarios`（任务类型映射到文档场景）
- `depth` → 允许的深度级别（shallow 只看 essential，medium 看 essential + recommended，deep 看全部）

## 二、章节组合规则

### 2.1 章节类型定义

#### Spec 章节

| 章节类型 | 适用场景 | 深度级别 | 说明 |
|---------|---------|---------|------|
| **数据契约** | impl, debug | essential | 接口签名、字段定义、类型约束 |
| **业务规则** | impl, review | recommended | 验证逻辑、状态转换、权限控制 |
| **API 语义** | impl, debug | essential | 参数行为、副作用、返回值约束 |
| **已知限制** | 所有场景 | essential | 不支持的场景、边界条件、临时方案 |

#### Flow 章节

| 章节类型 | 适用场景 | 深度级别 | 说明 |
|---------|---------|---------|------|
| **数据流图** | debug, arch | recommended/deep | Mermaid + 代码位置索引 |
| **设计意图** | review, arch | deep | 为什么这样设计、权衡取舍 |
| **状态迁移** | debug, arch | deep | 对象生命周期、并发模型 |
| **演进历史** | arch | recommended | 重构时间线、遗留代码解释 |

### 2.2 组合规则表

| 场景参数 | 抽离的章节 |
|---------|-----------|
| **新功能 + 浅层 + 前端** | 数据契约、API 语义、已知限制 |
| **新功能 + 中等 + 后端** | 数据契约、业务规则、数据流图、已知限制 |
| **新功能 + 深入 + 全栈** | 数据契约、业务规则、数据流图、设计意图、已知限制 |
| **Bug修复 + 中等 + 并发** | 数据流图、状态迁移、已知限制 |
| **架构优化 + 深入 + 后端** | 数据流图、设计意图、状态迁移、演进历史、已知限制 |

### 2.3 依赖解析

某些章节有前置依赖，必须先读前置章节才能理解当前章节。

**依赖关系示例**：
- **数据流图 → 设计意图**：必须先看清数据流，才能理解设计决策
- **数据契约 → 业务规则**：必须先理解数据结构，才能理解验证逻辑
- **演进历史 → 设计意图**：必须先了解时间线，才能理解当前决策

**脚本处理**：
- 使用拓扑排序自动补全依赖章节
- 示例：请求"调用链"章节时，自动包含"数据转换"章节

## 六、方案对比

### 6.1 与原方案对比

| 维度 | 原方案（多文档） | 本方案（按需抽离） |
|------|----------------|------------------|
| **文档数量** | 每个场景独立文档 | 一份完整文档 + 标记 |
| **维护成本** | 高（修改需同步多份） | 低（标记与内容在一起） |
| **信息一致性** | 难保证（多份文档容易不同步） | 保证（单一数据源） |
| **定制化** | 强（每个场景独立编写） | 强（通过参数组合） |
| **灵活性** | 差（增加场景需写新文档） | 强（调整参数即可） |

### 6.2 适用场景

**本方案适合**：
- ✅ 多场景复用同一份文档
- ✅ 文档内容有层次（浅/中/深）
- ✅ 章节之间有明确的依赖关系
- ✅ AI Agent 是主要消费者

**本方案不适合**：
- ❌ 完全不同的场景（无重叠内容）
- ❌ 文档结构完全不同（如 spec vs 用户手册）
- ❌ 纯人类阅读（标记会增加噪音）

## 七、关键设计原则

### 7.1 默认值原则

大部分章节使用默认属性：`scenarios: all, depth: essential`

只标记例外情况：
- 深入内容：`depth: deep`
- 特定场景：`scenarios: [arch]`
- 有依赖关系：`requires: ["chapter-id"]`

**理由**：减少标记负担，保持文档可读性

### 7.2 80/20 法则

80% 的任务是中等深度（根据真实统计），优先优化这个场景：
- `essential + recommended` 章节是核心价值
- `deep` 章节是少数深度任务的补充

### 7.3 单一数据源（SSOT）

所有内容写在一份文档中，通过标记区分，而不是维护多份文档。

**反模式**：
- ❌ spec-simple.md / spec-full.md（容易不同步）
- ❌ spec.md + spec-架构优化.md（重复内容）

**正确做法**：
- ✅ spec.md（完整文档 + 章节标记）

## 八、未来优化方向

### 8.1 智能标记建议

脚本可以分析文档内容，自动建议章节标记：
- 包含"为什么"、"权衡"的章节 → `depth: deep`
- 包含"Mermaid 图"、"调用链"的章节 → `scenarios: [debug, arch]`
- 包含"已知限制"、"临时方案"的章节 → `depth: essential`

### 8.2 动态场景定义

允许用户自定义场景（不局限于 impl/debug/review/arch），如：
- `scenarios: [performance-tuning]`
- `scenarios: [security-review]`
- `scenarios: [migration]`

### 8.3 多文档联合抽离

支持同时抽离多个文档的相关章节：
```bash
python doc_extract.py \
  docs/specs/agent-call.md \
  docs/flows/agent-lifecycle.md \
  --task-type architecture --depth deep
```

输出包含两个文档的相关章节，按依赖关系排序。
