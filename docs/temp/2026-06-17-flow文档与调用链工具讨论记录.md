## 已明确的工具需求

### 现有工具

1. **ast_scanner.py** → `ast_scan_result.json`
   - 全量扫描，一次性生成
   - 输出：所有函数的 `calls_to` 和 `called_by` 关系
   - 格式：JSON 结构化数据
   - 优点：快速、精确
   - 限制：AST 无法解析动态调用（如 `getattr(obj, "method")()`）

2. **func_search.py**
   - 按需查询，基于 grep
   - 输入：函数名（短名称，如 `send_message_to_agent`）
   - 输出：文本格式，包含定义位置、被调用位置
   - 优点：能找到 AST 无法解析的调用
   - 限制：同名函数可能混淆（见 `docs/temp/代码搜索/限制说明.md`）

### 计划中的整合工具（未实现）

**目标**：拼接 AST 扫描结果，提供第一层调用链

**输入**：
- 函数签名（`模块.函数名` 格式）

**输出**：
- 该函数的 `calls_to` 列表（函数内部调用了哪些函数）
- 格式：
  ```json
  [
    {"to": "core.orchestration.group_chat.StateError", "line": 602},
    {"to": "core.orchestration.group_chat.render_for_chat", "line": 617},
    {"to": "core.orchestration.group_chat.getattr", "line": 620}
  ]
  ```

**数据源**：
- 从 `ast_scan_result.json` 读取

**未决问题**：
- 是否需要同时输出 `called_by`（被谁调用）？

## 讨论中明确的关键概念

### 1. "跨模块"的定义

**模块边界**：第一层级文件夹
- `api`、`mcp`、`core`、`agents_hub`、`frontend`

**判断标准**：
- `api → core` ✅ 跨模块
- `core.orchestration → core.foundation` ❌ 不跨模块

---

### 2. "分支节点"的定义

**正确理解**：Flow 对象的业务分支，不是代码的 `if/else`

**示例**：
```python
# ✅ 必须记录（Flow 对象的分支）
if msg.type == "user":
    handle_user_message()
elif msg.type == "agent":
    handle_agent_message()

# ❌ 不记录（配置分支）
if settings.DEBUG:
    use_mock_llm()
```

---

### 3. "数据持久化"的定义

**包括**：
- 写入数据库
- 写入文件系统

**不包括**：
- 日志记录
- 内存缓存

---

### 4. "信息外漏"→"数据持久化"

**讨论过程**：
- 最初提出"信息外漏"概念，但定义模糊
- 讨论后明确为"数据持久化"

---

### 5. Spec 与 Flow 的关系

**比喻**：
- Spec = 平行面（某个模块的接口、约束）
- Flow = 跨平面的线（跨模块的数据流）

**分工**：
- Spec 写"是什么"（状态机定义、业务规则）
- Flow 写"怎么做"（代码路径、函数调用）
- 适度重复是正常的，不追求完全分离

---
