## Overview

**业务问题**：团队协作中存在需要多轮迭代的场景（如 Executor-Reviewer、Writer-Editor 模式），当前的单次消息派发无法满足这种循环执行需求。

**核心职责**：
- 定义多节点循环编排模型（至少 2 个节点，有且仅有 1 个 TERMINATOR）
- 管理循环定义的生命周期（创建 → 启动多次 → 删除）
- 管理执行实例的生命周期（创建 → 运行 → 完成/失败）
- 提供输出校验和重试机制
- 通过 MCP 工具暴露循环管理接口
- 实现轻量级内存管理，保持单个 Execution 在内存

**设计理念**：
- Loop 是可复用的模板，LoopExecution 是一次性执行实例
- 同一 Loop 可以多次启动，每次传入不同的 initial_task
- 内存中同时只保持单个 LoopExecution，避免累积
- 支持查询完整的执行历史

**不做什么**：
- 不负责具体的 Agent 执行逻辑（由 Agent 自身处理）
- 不管理群聊消息历史（由 GroupChat 处理）
- 不处理 Agent 的上下文压缩（由 context 层处理）
- 不支持 checkpoint 或状态恢复（PAUSED Execution 重启后从头开始）

#### LoopStatus 枚举

```python
class LoopStatus(str, Enum):
    CREATED = "created"       # 已创建，待启动
    RUNNING = "running"       # 运行中
    PAUSED = "paused"         # 已暂停
    COMPLETED = "completed"   # 已完成
    FAILED = "failed"         # 失败
```

### 状态机规则

```
CREATED  ──→  RUNNING
RUNNING  ──→  PAUSED | COMPLETED | FAILED
PAUSED   ──→  RUNNING | FAILED
COMPLETED ──→ (终态)
FAILED   ──→ (终态)
```

**状态转换约束**：
- CREATED → RUNNING：启动循环时
- RUNNING → PAUSED：手动停止循环时
- RUNNING → COMPLETED：TERMINATOR 节点返回 `should_continue=false`
- RUNNING → FAILED：达到最大循环次数、输出校验失败超过重试次数、执行异常
- PAUSED → RUNNING：恢复已暂停的循环
- PAUSED → FAILED：恢复失败时
- COMPLETED/FAILED：终态，不可转换

### 创建校验规则

<key_function last_update="2026-06-21T10:00:00+08:00">

  - loop_manager.LoopManager.create_loop:104

创建循环时执行以下校验：
1. `max_iterations` 必须大于 0
2. 节点数量至少 2 个
3. 有且仅有 1 个 TERMINATOR 节点
4. 所有 `agent_name` 必须在 RoleManager 中存在
5. 该群聊没有其他 RUNNING 状态的循环

### 输出校验机制

**普通节点校验**：
- 检查 `output_schema_fields` 中的每个字段是否在输出中存在
- 使用简单字符串匹配（`field in output`）

**TERMINATOR 节点校验**：
- 先校验业务字段（同普通节点）
- 再用正则解析 `<loop_decision>` 和 `<should_continue>` 标签
- 如果缺少标签，系统会要求重新输出

### 重试机制

- 复用同一个 `call_id` 避免创建新 AgentCall
- 每次重试附加错误提示和上一次输出
- 超过 `max_retries` 次抛出 `LoopExecutionError`

- 格式：`[循环-节点{send_from}-第{iteration}轮] @{send_to} {content}`
- 示例：`[循环-节点执行者-第1轮] @审查者 请审查这段代码`

**XML 标签定义**（`renderer.Tag` 枚举）：
- `<LOOP_NODE_ROLE>` -- 循环节点职责描述
- `<LOOP_OUTPUT_SCHEMA>` -- 循环节点输出格式要求
- `<PREVIOUS_NODE_OUTPUT>` -- 上一个节点输出
- `<LOOP_TERMINATION_CHECK>` -- 终止节点退出判断提示

### 持久化策略

**文件路径**：`local_data/teams/<team_name>/<project_path>/<group_chat_id>/loops.jsonl`

**格式**：append-only JSONL，每次状态变更追加一条记录

**容错机制**：
- 同一 `loop_id` 多条记录取最新
- 删除操作使用墓碑记录（`_deleted: true`）

### 内存管理策略

**设计原则**：
- Loop 是无状态工具，内存占用固定（每个 Loop 约 1-5 KB）
- 内存中同时只保持单个 Loop
- 不自动加载历史 Loop（懒加载）

**初始化行为**：
- `LoopManager.__init__()` 时，`_loops = {}`（空字典）
- 不调用 `_load_from_persistence()`

**内存清理时机**：
1. **创建新 Loop**：`create_loop()` 清空 `_loops` 中所有旧 Loop
2. **启动 Loop**：`start_loop()` 清空其他 Loop（保持唯一）
3. **显式删除**：`delete_loop()` 从 `_loops` 移除
4. **群聊销毁**：GroupChat 生命周期结束自动清空

**保留在内存的情况**：
- **RUNNING**：正在执行，必须保留
- **PAUSED**：暂停但未删除，必须保留（用户可能查询或恢复）
- **COMPLETED/FAILED**：完成后保留，方便查询状态（前端显示）

**懒加载机制**：
- `start_loop(loop_id)`：Loop 不在内存时从 JSONL 加载
- `get_loop_status(loop_id)`：Loop 不在内存时从 JSONL 加载
- `get_loop(loop_id)`：Loop 不在内存时抛出 `LoopNotFoundError`（内部方法）

**`list_loops()` 实现**：
- 直接读取 JSONL 文件，不依赖内存
- 返回所有 Loop 的摘要信息（包括 `in_memory` 标记）

### 异常体系

| 异常类 | 错误码 | 用途 |
|--------|--------|------|
| `LoopNotFoundError` | LOOP_NOT_FOUND | 循环不存在 |
| `LoopValidationError` | LOOP_VALIDATION_ERROR | 创建校验失败 |
| `LoopStateError` | LOOP_STATE_ERROR | 状态转换非法 |
| `LoopExecutionError` | LOOP_EXECUTION_ERROR | 执行失败 |

## Design Rationale

### 为什么使用事件驱动的节点完成通知？

**设计决策**：使用 `asyncio.Queue` 作为 `completion_queue`，Agent 处理完消息后向队列投递完成事件，LoopExecutor 监听队列继续下一个节点。

**理由**：
- 避免轮询，降低资源消耗
- 支持异步并发，提高执行效率
- 与现有的 Agent 消息处理机制自然集成

### 为什么使用 LOOP_MESSAGE 类型隔离上下文？

**设计决策**：循环内部消息使用 `MessageType.LOOP_MESSAGE` 标记，通过 `GroupChat.send_message_to_agent()` 保存到群聊历史，但在构造 LLM prompt 时跳过 runtime 注入。

**理由**：
- **保存到群聊历史**：Manager 需要通过群聊消息了解循环执行动态，复用现有的消息持久化机制，不需要单独设计 Loop 日志系统
- **跳过 runtime 注入**：循环节点只需关注当前任务（`<LOOP_NODE_ROLE>` / `<PREVIOUS_NODE_OUTPUT>`），不需要 `<runtime>` 中的 `team_members`、`group_chat_id` 等群聊上下文
- **渲染格式区分**：循环消息使用 `[循环-节点{name}-第{N}轮]` 前缀，在群聊历史中有明确标识

### 为什么 TERMINATOR 节点必须输出 `<loop_decision>` 标签？

**设计决策**：TERMINATOR 节点必须在输出末尾包含 `<loop_decision>` XML 标签，明确表示循环是否继续。

**理由**：
- 提供明确的退出信号，避免歧义
- 支持结构化解析，便于系统判断
- 允许 TERMINATOR 节点说明退出原因

### 为什么达到最大循环次数标记为 FAILED 而不是 COMPLETED？

**设计决策**：当 `current_iteration > max_iterations` 时，循环状态设为 FAILED，`error_message` 设为 "达到最大循环次数"。

**理由**：
- 设计者认为"达到最大循环次数"意味着任务可能未完成（TERMINATOR 没有主动说"完成了"）
- FAILED 状态更明确地表示"任务未按预期完成"
- Manager 可以根据 `error_message` 决定是否重新启动循环

**已知限制**：
- 这个设计可能不符合所有场景的预期
- 未来可能需要增加 `MAX_ITERATIONS_REACHED` 状态

### 为什么使用回调注入方案实现 WebSocket 通知？

**设计决策**：LoopExecutor 通过 `on_state_change` 回调参数接收状态变化通知函数，由 GroupChat 在创建 LoopExecutor 时注入实现。

**回调触发时机**：
- `_cleanup()`：Loop 完成或失败时
- `_emergency_stop()`：Loop 紧急停止时
- `_handle_node_completion()`：节点切换时（current_node_index 变化）

**理由**：
- 与现有的 `_notify_manager_loop_ended` 模式一致，保持代码风格统一
- LoopExecutor 不直接依赖 realtime 模块，保持职责单一
- 回调注入便于测试，可以 Mock 验证调用行为
- `_emergency_stop()` 和 `_cleanup()` 中回调调用包裹在 try/except 中，避免阻止清理逻辑

**实现细节**：
- `LoopExecutor.__init__()` 新增 `on_state_change: Callable[[str], None] | None = None` 参数
- `_notify_state_change()` 方法调用回调，传入 loop_id
- GroupChat.create_and_start_loop() 创建回调，回调实现调用 `broadcast_group_chat_refresh(group_chat_id)`
