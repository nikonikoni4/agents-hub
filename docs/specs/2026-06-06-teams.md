## Overview

**业务问题**：系统需要一种方式将多个角色（role）组织成预设集合，在创建群聊时快速复用，避免每次手动指定成员列表。

**核心职责**：
- 团队的全生命周期管理（创建、查询、更新、删除）
- 团队成员列表管理（角色名称集合）
- 成员有效性验证（通过 RoleManager 确认角色存在）
- 持久化到 JSON 文件

**不负责**：团队的运行时调度、消息传递、群聊管理、角色配置管理。

## Scope

### 范围内

- 团队 CRUD 操作
- 团队成员列表管理（role 名称列表）
- 成员验证（调用 RoleManager 验证 role 是否存在）
- 持久化到 `config.data_path/teams/teams.json`
- HTTP API 接口

### 范围外

- 团队的运行时调度逻辑（由 core/orchestration 负责）
- 团队与群聊的绑定关系（由 GroupChat 负责，参见 [group-chat-api spec](2026-06-03-group-chat-api.md)）
- 角色配置的 CRUD（由 roles 模块负责）
- 消息传递和会话管理
- 团队权限管理
- 团队模板功能

## Technical Contract

### API 端点

所有端点挂在 `/teams` 前缀下。

| 方法 | 路径 | 说明 | 路由处理函数 |
|------|------|------|-------------|
| GET | `/teams` | 列出所有团队 | `list_teams` |
| GET | `/teams/{name}` | 获取单个团队 | `get_team` |
| POST | `/teams` | 创建团队 | `create_team` |
| PATCH | `/teams/{name}` | 更新团队信息（PATCH 语义，仅更新传入字段） | `update_team` |
| DELETE | `/teams/{name}` | 删除团队 | `delete_team` |

### Request Schemas

**TeamCreateRequest**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | str | 是 | 团队名称 |
| members | list[str] | 是 | 成员角色名称列表 |

**TeamUpdateRequest**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | str \| None | 否 | 新的团队名称，为 None 时保持原名称 |
| members | list[str] \| None | 否 | 新的成员列表，为 None 时保持原成员列表 |

### Response Schema

**TeamResponse**

| 字段 | 类型 | 说明 |
|------|------|------|
| name | str | 团队名称 |
| members | list[str] | 成员角色名称列表 |

### 数据模型

**TeamInfo**（领域模型）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | str | 是 | 团队名称（唯一标识） |
| members | list[str] | 是 | 成员角色名称列表，至少包含一个成员 |

**持久化格式**：保存到 `config.data_path/teams/teams.json`，采用 JSON 数组格式。

### 业务规则

**成员验证**：
- 创建/更新团队时，必须验证成员列表中每个角色是否存在（通过 RoleManager）
- 成员列表为空时拒绝操作
- 包含不存在的角色时拒绝操作，返回无效成员列表和可用角色列表

**名称唯一性**：
- 团队名称作为唯一标识，不允许重复
- 更新名称时检查新名称是否与其他团队冲突

### 异常类型

| 异常 | 基类 | 触发场景 | HTTP 状态码 |
|------|------|----------|------------|
| TeamNotFoundError | ResourceNotFoundError | 获取/更新/删除不存在的团队 | 404 |
| TeamAlreadyExistsError | ValidationError | 创建时名称已存在，或更新时新名称冲突 | 409 |
| InvalidTeamMembersError | ValidationError | 成员列表包含不存在的角色 | 422 |
| EmptyTeamMembersError | ValidationError | 成员列表为空 | 422 |

所有异常继承自项目统一异常基类，由全局异常处理器转换为 HTTP 错误响应。

### API 架构分层

```
route -> service -> manager
```

- **route**：HTTP 入口，只做参数接收和响应转换
- **service**：业务协调，编排 manager 调用
- **manager**：领域逻辑

路由通过 FastAPI `Depends` 注入 Service 实例，禁止在路由中直接实例化。路由层禁止 try/except，所有异常由全局异常处理器统一处理。

## Design Rationale

**为什么团队只是角色名称的集合？**
- 团队的定位是群聊创建的预设模板，不需要复杂的成员属性
- 角色名称作为成员标识，与 roles 模块的 SSOT 保持一致
- 避免引入成员角色分配（manager/worker 等）带来的复杂度

**为什么使用 JSON 文件而非数据库？**
- 团队数据量小、变更频率低，JSON 文件足够
- 与 config.data_path 的数据路径策略一致
- 简化部署，不需要额外的数据库依赖

**为什么需要成员验证？**
- 防止创建包含无效角色的团队，避免群聊初始化时失败
- 提前暴露问题，提供清晰的错误信息（无效成员 + 可用角色列表）

**有哪些约束？**
- 成员验证依赖 RoleManager，需要 roles 模块先初始化
- JSON 文件的并发读写需要锁机制保护

**有哪些已知限制？**
- 不支持团队成员的角色分配（如 manager/worker 区分）
- 不支持团队模板功能
- 不支持团队权限管理
