## Overview

**业务问题**：系统需要统一的配置管理机制，避免配置散落在各模块中，同时需要跨模块共享的枚举定义。

**核心职责**：
- 以单例模式提供统一的配置访问入口
- 管理数据路径策略、MCP 端口、Docker 沙箱参数等系统级配置
- 定义跨模块共享的 Agent 平台和角色类型枚举
- 提供 CLI 工具路径映射（宿主机与 Docker 容器内）

## Scope

### 范围内

- 数据路径策略：三级路径优先级解析（migration > packaged > dev）
- 配置持久化：将用户自定义配置写入 YAML 文件
- 配置聚合：通过 `Config` 类提供统一快捷访问入口
- 枚举定义：`AgentPlatform`、`RoleType` 跨模块共享
- CLI 路径常量：宿主机与 Docker 容器内的 CLI 工具路径映射
- User 名称规范化：展示名后缀处理和身份判断

### 范围外

- Agent 业务逻辑配置（由 roles 模块负责）
- 群聊运行时配置（由 core 层负责）
- 前端配置管理

## Design Rationale

**为什么这样设计？**
- **单例模式**：配置是全局状态，单例确保所有模块访问同一份配置，避免同步问题
- **Config 聚合类**：提供统一入口（`config.data_path`），简化调用方代码，同时保留底层 `SystemConfig` 的完整性
- **三级路径优先级**：支持开发环境、打包环境、用户自定义三种场景，优先级明确
- **配置持久化**：用户自定义配置自动保存到 YAML，重启后生效
- **枚举定义在 types.py**：避免循环依赖，被多个模块共享

**有哪些约束？**
- 配置文件路径固定，不随数据路径迁移（配置文件本身不迁移）
- `null` 值不覆盖默认值，只持久化用户明确设置过的配置项
- User 名称规范化规则：除默认值 "user" 外，所有用户身份名自动追加后缀 "(user)"

**有哪些已知限制？**
- 当前只支持单用户配置，不支持多用户场景
- 配置项变更后需要重启服务才能生效（除 data_path 外）
